# 12. UI Design System

**Asumsi kerja:** dokumen ini melengkapi 11. Frontend Specification. Stack styling: Tailwind CSS + shadcn/ui. Filosofi visual mengikuti prinsip produk di blueprint — calm, calendar-centric, tidak boleh terasa seperti dashboard trading/fintech yang agresif, karena produk finansial yang bikin user cemas gagal validasi hipotesis "planning bukan tracking" (Section 1 Blueprint).

---

## 12.1 Prinsip Desain

1. **Calendar adalah pusat gravitasi visual** — semua halaman lain (Wallet, Budget, Goal) adalah halaman manajemen sekunder untuk operasi CRUD detail, bukan tempat user "tinggal". Desainnya boleh lebih fungsional/plain; Calendar yang mendapat alokasi polish terbesar.
2. **Warna membawa makna, bukan dekorasi** — status finansial (aman/waspada/kritis) harus terbaca dari warna tanpa membaca teks, konsisten di semua halaman.
3. **Tenang, bukan mendesak** — hindari warna merah/urgent berlebihan untuk hal yang sebenarnya informatif, bukan darurat. Reserve merah murni untuk saldo negatif nyata atau Goal yang benar-benar terlambat.
4. **Kepadatan rendah, kejelasan tinggi** — sesuai Kano Model (Section 3), Calendar adalah Performance feature: makin baik integrasinya makin tinggi kepuasan, tapi ini dicapai lewat kejelasan info, bukan menjejalkan lebih banyak elemen visual per tanggal.

## 12.2 Skema Warna Semantik

| Peran                                 | Token Tailwind (contoh)                     | Nama token CSS (`app/globals.css`)       | Kapan dipakai                                                                                                                |
| ------------------------------------- | ------------------------------------------- | ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Aman / income / on-track              | `emerald-600` (light), `emerald-400` (dark) | `--safe` / `--safe-foreground`           | Saldo positif, Goal on-track, Budget di bawah 80%                                                                            |
| Waspada                               | `amber-500`                                 | `--warning` / `--warning-foreground`     | Budget 80-99%, Forecast mendekati ambang, Goal mendekati deadline                                                            |
| Kritis                                | `rose-600`                                  | `--critical` / `--critical-foreground`   | Saldo negatif/proyeksi negatif, Budget melewati 100%, Goal terlambat                                                         |
| Netral/struktural                     | `slate-500` / `slate-200` (border)          | `--neutral` / `--neutral-foreground`     | Teks sekunder, border card, elemen non-status                                                                                |
| Aksen interaktif (tombol utama, link) | `indigo-600`                                | **`--brand`** / **`--brand-foreground`** | CTA utama, elemen yang bisa diklik — **dipisah dari warna status** supaya "tombol biru" tidak tertukar makna dengan "status" |

**Nama token resmi untuk aksen interaktif adalah `--brand` (utility Tailwind: `bg-brand` / `text-brand-foreground`), BUKAN `--accent` / `--color-accent`.** shadcn sudah memakai nama `--accent`/`--color-accent` untuk warna hover/highlight netral bawaan di `Button`/`Card`/dsb (di-generate `shadcn init`, lihat `app/globals.css`) — token itu abu-abu netral, bukan warna brand. Kalau sebuah revisi dokumen atau prompt menamai ulang token brand jadi "accent" karena itu istilah Inggris paling wajar untuk "aksen", itu akan menimpa `--accent` shadcn dan mewarnai semua hover state jadi biru/indigo tanpa disadari. **Kata "aksen"/"accent" di prosa dokumen ini adalah istilah desain (peran warna), bukan nama token — nama token yang valid untuk disalin ke kode selalu `--brand`.** Kelas kesalahan yang sama dengan insiden penamaan Nuxio/Nuvio sebelumnya: nama yang "kelihatan benar secara bahasa" tapi sudah dipakai untuk hal lain.

**Aturan penting**: warna status (emerald/amber/rose) tidak pernah dipakai untuk tombol aksi biasa, dan sebaliknya `--brand` tidak dipakai untuk menandakan status finansial — supaya user tidak salah membaca tombol sebagai sinyal risiko atau sebaliknya.

Dark mode: semua token di atas punya pasangan varian lebih redup/gelap (`-400` alih-alih `-600` untuk fill dengan background gelap) supaya tidak neon — konsisten dengan prinsip "tenang, bukan mendesak" juga berlaku di dark mode. Nilai OKLCH persis tiap token dan verifikasi kontrasnya ada di §12.8 "Verifikasi tampilan nyata".

## 12.3 Tipografi

- Font dasar: sans-serif sistem (`font-sans` Tailwind default, misal Inter) — tidak perlu font custom untuk MVP, ini bukan area diferensiasi produk.
- Skala: `text-sm` (14px) untuk label sekunder/subtitle, `text-base` (16px) untuk body, `text-lg`/`text-xl` untuk angka penting (saldo, progress), `text-2xl` khusus untuk headline saldo/proyeksi di Calendar (elemen paling penting di halaman paling penting).
- Bobot: hanya `font-normal` (400) dan `font-medium` (500) untuk sebagian besar UI; `font-semibold` (600) dibatasi untuk angka besar (saldo, target Goal) supaya tidak semua teks terasa berat.

## 12.4 Komponen Inti (shadcn/ui sebagai basis)

| Komponen shadcn/ui | Dipakai untuk                                                                                                             |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| `Dialog`           | `DayDetailPanel` (bisa sebagai slide-over/sheet variant), form tambah Wallet/Budget/Goal                                  |
| `Sheet`            | Alternatif Dialog untuk panel yang slide dari samping (lebih sesuai untuk `DayDetailPanel` yang muncul dari klik tanggal) |
| `Card`             | `WalletCard`, `GoalCard`, ringkasan Budget                                                                                |
| `Progress`         | `BudgetProgressBar`, `GoalCard` progress bar                                                                              |
| `Badge`            | `EventBadge` di Calendar, status label (on-track/terlambat)                                                               |
| `Skeleton`         | Loading state Calendar grid dan list, sesuai 11.5                                                                         |
| `Toast` (sonner)   | Konfirmasi aksi (bukan kata "berhasil" — lihat 12.6 Copywriting)                                                          |
| `Tabs`             | Switch antar tampilan jika dibutuhkan (misal filter kategori Transaction)                                                 |

**Kenapa shadcn/ui**: komponen ini di-copy langsung ke repo (bukan npm dependency yang di-update terpisah), jadi tim bisa kustomisasi warna/style sesuai token di atas tanpa terkunci ke versi library — penting untuk timeline 32 hari yang tidak punya slot waktu untuk debug breaking changes dari library UI pihak ketiga.

## 12.5 Pola Komponen Spesifik Produk

### DayCell (Calendar)

- Ukuran konsisten (aspect-square atau mendekati), tidak boleh berubah tinggi antar tanggal meski jumlah entri beda-beda (mencegah layout shift saat navigasi bulan)
- Maksimal 3 indikator dot per tanggal (lihat 11.4), warna dot mengikuti tipe (income = emerald, expense = default slate/netral kecuali melewati budget = amber/rose, bill = indigo muda, goal milestone = badge berbeda bentuk bukan cuma warna — supaya tidak mengandalkan warna semata untuk aksesibilitas)
- Tanggal hari ini mendapat outline/border berbeda (bukan warna fill berbeda, supaya tidak tertukar dengan status finansial)

### ForecastOverlay

- Garis proyeksi ditampilkan sebagai overlay tipis di atas grid (bukan chart terpisah), warna mengikuti status (emerald jika proyeksi tetap positif, transisi ke amber/rose mendekati dan melewati nol)
- Tanggal pertama proyeksi negatif (jika ada) mendapat marker visual eksplisit — ini insight paling bernilai dari Forecast (Section 4.7), jangan sampai tenggelam di keramaian visual Calendar

### ChatWindow (AI Copilot)

- Bubble AI dan bubble user dibedakan lewat posisi (kiri/kanan) dan warna latar (bukan warna status finansial — pakai `slate` netral untuk AI, `indigo` muda untuk user, supaya tidak konflik makna dengan skema warna status)
- Setiap klaim angka dari AI ditampilkan dengan sedikit visual "tertaut ke data" (misal small badge atau link kecil "lihat sumber") — mendukung Definition of Done AI: "jawaban bisa ditelusuri ke data riil"
- Disclaimer AI Budget Recommendation ("ini saran, bukan keputusan otomatis") tampil sebagai teks kecil `text-xs text-slate-500`, bukan warning box besar — supaya tidak terasa seperti peringatan bahaya padahal ini catatan biasa

### Empty state (pola umum semua halaman)

Ikon di atas, headline pendek (nama ruang kosongnya, bukan permintaan maaf), satu baris deskripsi, satu tombol CTA verb-first. Contoh pola:

```
[ikon]
Belum ada wallet lain
Tambah wallet kedua untuk memisahkan cash dan rekening bank kamu.
[Tambah wallet]
```

## 12.6 Copywriting

Konsisten dengan prinsip di Section 1 (produk yang menenangkan, bukan mendesak):

- **Sentence case**, bukan Title Case, di semua tombol/label/heading.
- **Verb-first pada CTA**: "Tambah wallet", bukan "Wallet baru" atau "Klik di sini".
- **Hindari kata "berhasil"** pada konfirmasi — toast cukup "Transaksi disimpan", bukan "Transaksi berhasil disimpan".
- **Tidak ada tanda seru** pada copy sistem (toast, label) — kesan tenang, bukan bersemangat berlebihan.
- **Bahasa orang kedua ("kamu")** untuk hal milik user: "Wallet kamu", bukan "Wallet saya" atau bentuk pasif kaku.
- **Disclaimer AI selalu eksplisit tapi tidak menakutkan** — "Ini saran berdasarkan pola pengeluaranmu, bukan keputusan otomatis" lebih baik daripada box peringatan besar berwarna merah.

## 12.7 Aksesibilitas Minimum (MVP-appropriate, bukan audit penuh)

- Kontras warna teks-background memenuhi minimum WCAG AA untuk teks body (bukan target AAA — di luar scope realistis 32 hari)
- Status finansial tidak pernah disampaikan lewat warna semata — selalu dipasangkan dengan bentuk/ikon/teks (misal Badge dengan label teks "Waspada", bukan cuma warna amber polos) untuk pengguna buta warna
- Semua elemen interaktif (`DayCell`, tombol) bisa difokus lewat keyboard (`Tab`) — komponen shadcn/ui sudah mendukung ini secara default selama tidak di-override dengan custom div tanpa semantik yang benar

## 12.8 Disiplin Anti-Slop (referensi: taste-skill + hallmark)

Dua skill anti-AI-slop terpasang di skill library lokal — `design-taste-frontend` (taste-skill, sumber [Leonxlnx/taste-skill](https://github.com/Leonxlnx/taste-skill)) dan `hallmark` (sumber [nutlope/hallmark](https://github.com/nutlope/hallmark)). Keduanya ditulis untuk landing page/portfolio dan **eksplisit menyatakan bukan untuk dashboard/product UI** — detail sumber dan skill FE terkait lain ada di **11.8 Frontend Specification**. Bagian ini hanya berisi aturan yang portable ke app UI Nuxio: kalibrasi warna, tipografi, kontras, dan daftar "AI tells" yang harus dihindari — bukan pattern landing page (hero, macrostructure, marketing copy) yang tidak relevan.

### Memperkuat 12.2 Skema Warna

- **Aksen interaktif (token CSS `--brand`, bukan `--accent` — lihat 12.2) adalah highlighter, bukan fill besar.** Dipakai untuk link, border, ring, dan tombol CTA — bukan untuk membanjiri satu section penuh warna. Ini sudah konsisten dengan aturan pemisahan aksen-vs-status di 12.2, hanya ditegaskan lagi: kalau ada dorongan menambah lebih banyak `indigo`, itu biasanya slop, bukan kebutuhan hierarki.
- **Elevation di dark mode = lebih terang, bukan lebih gelap.** Permukaan yang "naik" di atas background (`Dialog`, `Sheet`, `Card` yang di-hover) menambah ±3% lightness per level dari base surface — bukan menambah bayangan gelap yang malah hilang di dark mode.
- **Jangan pakai gradient dekoratif ungu→biru atau oranye→pink** di ilustrasi empty state atau splash screen — itu AI-tell paling dikenali. Kalau butuh gradient, maksimal 2-stop, dalam keluarga warna semantik yang sudah ada di 12.2 (bukan warna baru di luar tabel).

### Memperkuat 12.3 Tipografi

- **`Inter` di Nuxio bukan default asal-pakai** — ini keputusan sadar di bawah kategori "trust-first / accessibility-first" (produk finansial, keterbacaan lebih penting daripada personality tipografi), bukan karena belum sempat memilih font lain. Kalau ada kebutuhan diferensiasi visual di masa depan (v2), evaluasi lewat proses sadar yang sama — bukan ganti font diam-diam.
- **Angka uang wajib `font-variant-numeric: tabular-nums`** di semua tempat saldo/progress ditampilkan — `WalletCard`, `BudgetProgressBar`, headline saldo di Calendar, `GoalCard`. Supaya digit sejajar secara visual saat nilai berubah atau dibandingkan antar baris, bukan "melompat" karena lebar digit proporsional berbeda-beda.
- **Body text panjang dibatasi `max-w-[65ch]`** — narrative AI Copilot, deskripsi empty state, disclaimer. Baris yang terlalu lebar susah dibaca meski kontennya benar.

### Shape consistency lock

Satu skala radius per kategori komponen, didokumentasikan supaya tidak tercampur diam-diam:

- `Card`, `Dialog`, `Sheet` → radius default shadcn (`--radius`, umumnya 8px/`rounded-lg`).
- `Badge`, status pill (`EventBadge`, label on-track/terlambat) → `rounded-full`, khusus elemen kecil berbentuk pil.
- `Button` primer/sekunder → radius default shadcn, **sama** dengan `Card` — jangan jadi pill kalau `Card` di sekitarnya sudut tajam/medium.

### Checklist kontras (memperkuat 12.7)

Empat jebakan paling umum — cek sebelum ship komponen baru, bukan cuma andalkan "kelihatannya kontras":

1. **Background yang di-flip gelap tapi teks warisan warna default.** Kalau sebuah state (misal `DayCell` terpilih) mengubah background jadi gelap, rule yang sama wajib set warna teks eksplisit — jangan andalkan inheritance.
2. **Teks putih di atas tombol aksen.** Jangan asumsikan `text-white` selalu aman di atas `indigo-600` — verifikasi rasio kontras AA (4.5:1) tiap kali warna aksen berubah shade.
3. **Teks `slate-500` di atas card `slate-100`/`slate-200`.** Kombinasi ini sering jatuh di bawah 4.5:1 — naikkan ke `slate-600`/`700` atau turunkan lightness background.
4. **Focus ring warna sama dengan fill tombol yang di-focus.** Ring jadi tidak kelihatan. Pastikan warna ring focus punya kontras ≥3:1 terhadap elemen DAN halaman, bukan cuma "ada ring".

### Verifikasi tampilan nyata (gate sebelum Phase 1)

Angka kontras hasil hitung manual (waktu token dibuat) tidak dipercaya sampai lolos dua verifikasi independen — "lolos di atas kertas" tidak sama dengan "kelihatan jelas di layar", terutama untuk `critical`/`warning` (dua token alert finansial yang paling berisiko):

1. **Otomatis, per commit** — `__tests__/unit/design-tokens-contrast.test.ts` membaca `app/globals.css` langsung (bukan nilai hardcode terpisah) dan menghitung rasio WCAG tiap pasangan `--<token>`/`--<token>-foreground` (light + dark) pakai [culori](https://culorijs.org/) — library kontras pihak ketiga yang teruji, bukan implementasi OKLCH manual. Jalan otomatis tiap `npm test`/CI; token berubah tanpa update test yang lolos = gagal build.
2. **Manual, sekali per perubahan token** — screenshot browser nyata (Chrome via Playwright, bukan cuma render headless tanpa dilihat) untuk kelima swatch di light dan dark mode. Diverifikasi 2026-08-08: kelima pasangan (`critical`, `warning`, `safe`, `neutral`, `brand`) terbaca jelas di kedua mode, tidak ada yang pudar/washed-out — termasuk `critical`/`warning` yang jadi fokus utama. Halaman preview yang dipakai (`app/dev-token-preview/page.tsx`) sudah dihapus setelah verifikasi (bukan bagian aplikasi final); ulangi pola yang sama (swatch sederhana per token, panel `.dark` berdampingan) kalau perlu re-verifikasi setelah token berubah.

Token baru atau perubahan nilai token yang ada wajib lolos keduanya sebelum dipakai di komponen Phase 1+ — ini gate, bukan langkah opsional.

### State completeness

Setiap komponen interaktif baru mengikuti checklist 8-state di **11.8 Frontend Specification** — ini keputusan desain dan implementasi yang sama, tidak dipisah dokumen.

### Memperkuat 12.6 Copywriting

- Tanda baca: kutip lengkung (`" "`, `' '`), en dash `–` untuk rentang angka/tanggal (bukan `--`), elipsis `…` (bukan `...`).
- Hindari em dash `—` sebagai gaya penulisan di UI copy — pattern paling sering disalahgunakan model AI. Kalau butuh jeda, pecah jadi dua kalimat atau pakai koma.
- Error message tetap 3 bagian (apa yang salah → kenapa → apa selanjutnya) — cross-ref 11.8.
- Data dummy/seed untuk demo atau screenshot publik jangan pakai nama template generik ("John Doe", "Budi Santoso" berulang) — pakai variasi nama yang terasa nyata.
- **CTA generik dilarang**: "Get Started", "Learn More", "Try Now", "Explore", "Klik di sini" — sudah konsisten dengan aturan verb-first di 12.6, ini daftar konkret yang harus ditolak kalau muncul. Pakai aksi spesifik sesuai konteks ("Tambah wallet", "Lihat detail transaksi").
- **Buzzword marketing dilarang** di copy AI Copilot maupun notifikasi: "AI Powered", "Revolutionary", "Next-Gen", "Seamless", "Cutting Edge", "Powerful". Produk finansial yang tenang (12.1) butuh bahasa spesifik yang menjelaskan manfaat nyata, bukan klaim generik.

### AI-tell checklist khusus app UI

Hal yang harus dihindari di Nuxio secara spesifik (bukan daftar generik landing page):

- **Spinner lingkaran generik** untuk loading list/grid — pakai skeleton berbentuk sama seperti konten final (sudah jadi aturan di 11.5, ditegaskan lagi sebagai bagian disiplin anti-slop).
- **Dot dekoratif tanpa makna semantik.** Dot di `DayCell` sudah semantik (income/expense/bill, lihat 12.5) — jangan tambah dot baru di tempat lain (misal badge notifikasi kosong) tanpa makna status riil di baliknya.
- **Card-in-card** (border di dalam border) — misal `BudgetProgressBar` di dalam `DayDetailPanel` tidak perlu dibungkus card kedua kalau `DayDetailPanel` sendiri sudah jadi container visual.
- **Placeholder generik "Tidak ada data"** tanpa konteks — semua empty state mengikuti pola ikon + headline + deskripsi + CTA di 11.5/12.5; jangan regresi ke placeholder polos saat fitur baru ditambahkan setelah MVP.
- **Ikon dekoratif generik** (sparkle, magic wand, lightning, diamond, robot/orb AI) untuk merepresentasikan aksi finansial nyata — ikon harus literal sesuai aksinya (wallet, transfer, kalender, dst dari Lucide), bukan dekorasi yang terasa "AI-generated".
- **Bukan tell**: keseragaman ukuran/bentuk `DayCell`, `WalletCard`, `GoalCard` (lihat 12.5). Aturan umum "hindari feature card identik" yang berlaku di landing page **tidak berlaku di sini** — ini kartu data fungsional, keseragaman disengaja untuk scanability dan mencegah layout shift, bukan tanda template AI.

**Di luar scope aktif** (baru relevan kalau/ketika Nuxio membangun public marketing page — belum ada di MVP, lihat 11.1 & 12.9): larangan testimonial palsu, "Trusted by" logo bar generik, pricing card "Most Popular", FAQ template, layout Hero+3-card, footer 4 kolom. Dicatat di sini supaya tidak hilang, bukan diikuti sekarang.

## 12.9 Yang Sengaja Tidak Dibahas di MVP Ini

Sesuai prinsip Section 2 Blueprint (scope trade-off eksplisit), dokumen ini **tidak** mencakup:

- Design token untuk fitur Dashboard (karena Dashboard eksplisit ditunda ke fase berikutnya)

Kalau ada kebutuhan menambah area ini pasca-MVP, ini masuk dokumen Design System v2, bukan revisi dokumen ini di tengah eksekusi 32 hari — konsisten dengan mitigasi Scope Creep di Section 8 Blueprint.
