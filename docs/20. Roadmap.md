# 20. Roadmap.md — Eksekusi 32 Hari

> Dokumen ini adalah panduan eksekusi harian untuk tim 3 engineer selama 32 hari. Ini bukan dokumen aspirasi — ini adalah kontrak kerja tim dengan diri sendiri. Setiap perubahan scope di luar dokumen ini harus melalui proses eksplisit (lihat Section 20.6).

---

## 20.1 Prinsip Eksekusi

**Empat aturan yang tidak boleh dilanggar selama 32 hari:**

1. **Scope blueprint ini final.** Tidak ada fitur baru yang masuk tanpa menghapus sesuatu dari scope yang ada. Setiap "tambah sedikit saja" kumulatif menjadi alasan proyek tidak selesai.

2. **Staging sebelum production, selalu.** Tidak ada hotfix langsung ke production. Kalau darurat, staging dulu 30 menit, baru deploy.

3. **Hari buffer tidak boleh diisi fitur baru.** Hari buffer (setiap hari ke-7, 14, 21, 28) eksis untuk menyelesaikan yang belum selesai dari minggu itu — bukan untuk memulai fitur baru yang "sudah tergoda".

4. **AI Copilot dipotong duluan jika overrun, bukan Calendar.** Sesuai prioritas Kano: Calendar = Basic (tidak bisa dipotong), AI = Excitement (bisa dikurangi scope tanpa produk kehilangan nilai inti).

## 20.4 Dependency Map

```
Auth ──────────────────────────────────────────────────────────┐
  │                                                             │
  ▼                                                             ▼
Workspace ──────────────────────────────────────── Onboarding Wizard
  │
  ├──→ Wallet ──────────────────────────────────────────────┐
  │      │                                                   │
  │      ▼                                                   │
  │    Transaction ──────────────────────────────────┐      │
  │      │                                           │      │
  │      ├──→ Calendar (consumer) ◄──────────────────┤      │
  │      │      │                                    │      │
  │      │      ◄── RecurringRule (generator)        │      │
  │      │                                           │      │
  │      ├──→ Budget ──────────────────────→ Calendar layer │
  │      │                                           │      │
  │      ├──→ Goal ────────────────────────→ Calendar layer │
  │      │                                           │      │
  │      └──→ Forecast ─────────────────────→ Calendar overlay
  │             │
  │             └──→ AI Copilot (Fungsi 2: narasi Forecast)
  │
  └──→ AI Copilot (Fungsi 1: Spending dari Transaction)
                 (Fungsi 3: Budget Recommendation dari Budget)
```

**Implikasi dependency:**
- Wallet dan Transaction harus selesai sebelum Calendar bisa menampilkan data riil.
- Recurring engine harus selesai dan ter-test sebelum Forecast bisa dihitung.
- Forecast harus ada sebelum AI Cashflow Prediction bisa bekerja.
- AI Copilot adalah fitur paling "late" dalam dependency chain — wajar dikerjakan di Week 4.

## 20.6 Protokol Perubahan Scope

Jika ada tekanan untuk menambah atau mengubah scope di tengah eksekusi, gunakan protokol ini:

```
1. Tulis usulan perubahan secara eksplisit:
   "Ingin tambah fitur X karena alasan Y."

2. Identifikasi dampak ke timeline:
   "Ini membutuhkan N hari, yang berarti harus menunda/memotong Z."

3. Buat keputusan bersama (bukan satu orang):
   Ketiga engineer harus setuju sebelum scope berubah.

4. Update dokumen ini jika disetujui:
   Roadmap yang tidak diupdate setelah keputusan = roadmap yang tidak lagi dipercaya.
```
