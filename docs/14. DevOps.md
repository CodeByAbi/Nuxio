# 14. DevOps — Infrastructure & Deployment

> Dokumen ini menjabarkan pipeline deployment, manajemen environment, background jobs, dan monitoring untuk MVP 32 hari. Dibaca bersama `15. Security.md` (secret management, env vars) dan `13. AI.md` (LLM API endpoint management).

## 14.1 Filosofi DevOps MVP

Tiga prinsip yang menjaga DevOps tetap proporsional untuk tim 3 orang:

1. **Otomasi minimum yang benar-benar dipakai.** Jangan bangun pipeline canggih yang tidak ada yang maintenance-nya. CI/CD sederhana yang berjalan reliabel lebih baik dari pipeline kompleks yang kadang gagal misterius.

2. **Monolith dulu, bukan microservice.** Sesuai keputusan blueprint Section 7 — satu deployment unit (Next.js monolith), bukan multi-service yang butuh orchestration tambahan.

3. **Staging (environment) bukan opsional.** Setiap perubahan kode harus melewati environment staging — diwakili branch `develop` dengan deployment Vercel preview + Supabase project staging — sebelum production, terutama untuk aplikasi finansial di mana bug di production bisa langsung merusak data transaksi user.

## 14.3 Stack & Justifikasi

| Komponen | Pilihan MVP | Alasan |
|---|---|---|
| Hosting app | **Vercel** | Zero-config Next.js deployment, free tier cukup untuk MVP, built-in preview URL per PR |
| Database | **Supabase (PostgreSQL)** | Managed PostgreSQL + connection pooler (pgBouncer) bawaan, free tier 500MB cukup untuk MVP, dashboard visual untuk debugging data |
| Background jobs | **Vercel Cron** | Built-in di Vercel, tidak butuh infra tambahan, cukup untuk 2 job MVP (recurring generator + forecast recompute) |
| CI/CD | **GitHub Actions** | Gratis untuk repo publik/privat, integrasi native dengan Vercel |
| Secret management | **Vercel Environment Variables** | Enkripsi at rest, tidak pernah masuk ke kode atau git |
| Monitoring error | **Sentry** (free tier) | Error tracking minimal, cukup untuk MVP — jangan pasang APM penuh dulu |
| Logging | **Vercel Logs** | Built-in, tidak butuh setup tambahan untuk MVP |

## 14.4 Environment & Branch Strategy

### Tiga environment, tiga project Supabase terpisah

```
main branch        → Production   → Supabase project: namaapp-prod
develop branch     → Staging      → Supabase project: namaapp-staging
feature/* branches → Preview URL  → Supabase project: namaapp-dev (shared)
```

**Tidak ada branch `staging` terpisah.** Environment staging diwakili oleh branch `develop` (Vercel preview deployment dengan alias tetap), sehingga alur branch hanya: `feature/*` → PR → `develop` → PR → `main`. Database staging (project Supabase terpisah) tetap ada dan dipakai oleh deployment `develop`.

**PENTING:** Database dev/staging/prod harus benar-benar terpisah (project Supabase berbeda). Jangan pernah pakai database production untuk testing, sekalipun hanya "cek satu query".

### Environment variables per environment

```bash
# .env.local (development — tidak di-commit ke git)
SUPABASE_URL="http://127.0.0.1:54321"        # local Supabase (CLI) atau project dev
SUPABASE_ANON_KEY="<anon-key-local>"
SUPABASE_SERVICE_ROLE_KEY="<service-role-key-local>"
GEMINI_API_KEY="..."
CRON_SECRET="dev-secret-tidak-penting"

# Vercel Staging environment variables
SUPABASE_URL="https://<ref>.supabase.co"     # project staging
SUPABASE_ANON_KEY="<anon-key-staging>"
SUPABASE_SERVICE_ROLE_KEY="<service-role-key-staging>"
GEMINI_API_KEY="..."
CRON_SECRET="<generated-secret-staging>"

# Vercel Production environment variables
SUPABASE_URL="https://<ref>.supabase.co"     # project production
SUPABASE_ANON_KEY="<anon-key-prod>"
SUPABASE_SERVICE_ROLE_KEY="<service-role-key-prod>"   # BERBEDA dari staging
GEMINI_API_KEY="..."
CRON_SECRET="<generated-secret-prod>"
```

> **Aturan:** `SUPABASE_ANON_KEY` aman dibawa ke client **hanya karena RLS aktif** di seluruh tabel finansial. `SUPABASE_SERVICE_ROLE_KEY` (bypass RLS) dan `GEMINI_API_KEY` tidak pernah boleh sampai ke browser — hanya dipakai server-side (route handler / background job).

## 14.5 CI Pipeline (GitHub Actions)

```yaml
# .github/workflows/ci.yml
name: CI

on:
  pull_request:
    branches: [main, develop]
  push:
    branches: [develop]

jobs:
  ci:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'

      - name: Install dependencies
        run: npm ci

      - name: TypeScript check
        run: npx tsc --noEmit

      - name: Lint
        run: npm run lint

      - name: Unit tests
        run: npm test -- --coverage --passWithNoTests
        env:
          SUPABASE_URL: ${{ secrets.SUPABASE_URL_TEST }}
          SUPABASE_ANON_KEY: ${{ secrets.SUPABASE_ANON_KEY_TEST }}
          SUPABASE_SERVICE_ROLE_KEY: ${{ secrets.SUPABASE_SERVICE_ROLE_KEY_TEST }}

      - name: Build
        run: npm run build
        env:
          SUPABASE_URL: ${{ secrets.SUPABASE_URL_TEST }}
          SUPABASE_ANON_KEY: "ci-anon-key"
          SUPABASE_SERVICE_ROLE_KEY: "ci-service-role-key"
          GEMINI_API_KEY: "dummy-key-for-build"
          CRON_SECRET: "ci-secret"
```

**Aturan CI:**
- PR tidak bisa di-merge kalau CI gagal — ini dikonfigurasi sebagai branch protection rule di GitHub.
- Waktu target CI: < 3 menit. Kalau lebih dari itu, identifikasi test yang lambat dan optimalkan.

## 14.6 Database Migration Strategy

Menggunakan **Supabase CLI** (SQL migration — tidak ada ORM):

```bash
# Setup pertama kali
npx supabase init                    # buat folder supabase/ + config
npx supabase login                   # autentikasi CLI (akses token)
npx supabase link --project-ref <ref>  # hubungkan project (dev/staging/prod)

# Development: buat migration baru dari perubahan skema lokal
npx supabase db start                # jalankan Postgres lokal (Docker)
npx supabase db diff --use-migra     # diff perubahan skema vs migrasi
npx supabase migration new nama_migration   # buat file SQL kosong
# tulis DDL + enable RLS + policy di file migrasi, lalu:
npx supabase db push                 # apply ke database lokal / project ter-link
```

### Aturan migration

1. **Setiap PR yang mengubah schema DB wajib menyertakan file migration SQL (Supabase CLI)** — tidak boleh mengubah schema langsung di database (dashboard, psql manual) tanpa migration terdokumentasi.
2. **RLS menyatu dengan DDL.** Migrasi tabel baru wajib berisi `create table` + `alter table ... enable row level security` + policy — tabel tanpa RLS di migrasi yang sama adalah lubang isolasi (`07. Database.md` 7.8).
3. **Migration harus reversible** — setiap `ALTER TABLE ADD COLUMN` harus punya cara rollback yang terdokumentasi (`supabase db diff` + rollback SQL di PR description).
4. **Staging dulu, production kemudian.** Jalankan `supabase db push` di staging dan verifikasi data tidak rusak sebelum di-apply ke production.
5. **Jangan rename kolom atau drop kolom yang masih dipakai** — ini kategori migration destruktif yang butuh koordinasi eksplisit dan maintenance window.
6. **Migrasi bertipe uang** (kolom berubah pada data finansial) direview dua orang sebelum di-apply ke staging.

### Migrasi di pipeline deployment

Migrasi **tidak dijalankan otomatis di dalam `next build`** — dijalankan eksplisit di pipeline (manual/CI) ke staging dulu, diverifikasi, baru ke production:

```bash
# Staging (dari CI atau developer setelah link)
npx supabase link --project-ref <ref-staging>
npx supabase db push                 # apply migrasi yang belum jalan

# Production (setelah QA staging lolos)
npx supabase link --project-ref <ref-prod>
npx supabase db push
```

Ini memastikan migrasi diverifikasi di staging sebelum menyentuh production — tidak ada perubahan skema yang berjalan sebagai side-effect build yang tidak terkontrol.

## 14.7 Background Jobs

MVP membutuhkan dua background job. Keduanya menggunakan Vercel Cron.

### Job 1: Recurring Bill Generator

**Fungsi:** Meng-generate occurrence bill berulang untuk 60 hari ke depan berdasarkan recurring rules yang didefinisikan user.

**Jadwal:** Setiap hari pukul 00:05 WIB (UTC+7 → UTC 17:05 sebelumnya).

```yaml
# vercel.json
{
  "crons": [
    {
      "path": "/api/jobs/generate-recurring",
      "schedule": "5 17 * * *"
    },
    {
      "path": "/api/jobs/recompute-forecast",
      "schedule": "15 17 * * *"
    }
  ]
}
```

```typescript
// lib/supabase/admin.ts — service role client (hanya server-side)
import { createClient } from '@supabase/supabase-js';

export const supabaseAdmin = createClient(
  process.env.SUPABASE_URL!,
  process.env.SUPABASE_SERVICE_ROLE_KEY!,
  { auth: { persistSession: false } }
);

// /api/jobs/generate-recurring.ts
export async function GET(request: Request) {
  // Verifikasi request datang dari Vercel Cron (bukan request sembarang)
  const authHeader = request.headers.get('authorization');
  if (authHeader !== `Bearer ${process.env.CRON_SECRET}`) {
    return Response.json({ error: 'Unauthorized' }, { status: 401 });
  }

  try {
    // Service role = bypass RLS → WAJIB scope workspace_id manual
    const { data: rules, error } = await supabaseAdmin
      .from('recurring_rules')
      .select('id, workspace_id, workspace:workspaces(*)')
      .eq('is_active', true);

    if (error) throw error;

    // Generate occurrence untuk 60 hari ke depan per rule
    for (const rule of rules ?? []) {
      await generateOccurrences(rule, 60);
    }

    return Response.json({ success: true, processed: (rules ?? []).length });
  } catch (error) {
    // Log ke Sentry
    Sentry.captureException(error);
    return Response.json({ error: 'Job failed' }, { status: 500 });
  }
}
```

**Edge case yang wajib ditangani di dalam `generateOccurrences`:**
- Tanggal 31 di bulan yang tidak punya tanggal 31 → mundur ke hari terakhir bulan tersebut.
- Tanggal 29 Februari di tahun bukan kabisat → mundur ke 28 Februari.
- Duplikasi occurrence (job jalan dua kali karena Vercel retry) → gunakan insert dengan unique constraint `(recurring_rule_id, due_date)` di level database, bukan cek di kode saja.

### Job 2: Forecast Recompute

**Fungsi:** Menghitung ulang proyeksi saldo untuk semua workspace aktif dan menyimpan snapshot-nya.

**Jadwal:** 10 menit setelah Job 1 (00:15 WIB) — memastikan recurring occurrences sudah ter-generate sebelum forecast dihitung.

**Logika forecast (rule-based):**
```
forecastBalance(date) =
  currentBalance
  + Σ scheduledIncome(date)
  - Σ scheduledBills(date)
  - avgDailyNonRecurringExpense × daysFromNow(date)
```

Di mana `avgDailyNonRecurringExpense` dihitung dari transaksi manual 30 hari terakhir per kategori. Jika tidak ada histori, komponen ini = 0 (bukan error — tapi UI harus menampilkan keterangan "proyeksi terbatas").

## 14.8 Monitoring & Alerting

### Error tracking (Sentry)

```bash
npm install @sentry/nextjs
npx @sentry/wizard@latest -i nextjs
```

Yang wajib di-track di Sentry:
- Semua unhandled exception di API routes.
- Error dari LLM API (timeout, rate limit, 5xx).
- Kegagalan background job (Job 1 & Job 2).
- Error validasi respons AI (halusinasi terdeteksi).

Yang **tidak** perlu di-track di Sentry untuk MVP:
- 404 errors (terlalu noisy).
- Validasi input user yang gagal (ini expected behavior).

### Health check endpoint

```typescript
// /api/health
import { supabaseAdmin } from './lib/supabase/admin';

export async function GET() {
  try {
    await supabaseAdmin.from('wallets').select('id').limit(1);  // cek koneksi DB
    return Response.json({
      status: 'ok',
      timestamp: new Date().toISOString(),
      database: 'connected',
    });
  } catch {
    return Response.json({ status: 'error', database: 'disconnected' }, { status: 503 });
  }
}
```

Endpoint ini dipanggil oleh Vercel monitoring (atau layanan uptime monitor seperti UptimeRobot) setiap 5 menit.

### Log yang wajib ada

Setiap API request yang menyentuh data finansial harus mencatat:
```typescript
console.log(JSON.stringify({
  event: 'transaction.created',
  workspaceId,
  userId,
  amount,  // bukan data sensitif seperti nama/deskripsi
  timestamp: new Date().toISOString(),
}));
```

## 14.9 Deployment Checklist (sebelum setiap deploy ke Production)

### Pre-deploy
- [ ] Semua CI checks passing di branch develop
- [ ] Migration di-test di environment staging dan tidak merusak data
- [ ] Environment variables production sudah dikonfigurasi (verifikasi via Vercel dashboard, bukan asumsi)
- [ ] API key LLM valid dan quota tidak hampir habis
- [ ] Sentry DSN terkonfigurasi untuk production environment

### Post-deploy
- [ ] `/api/health` mengembalikan status `ok`
- [ ] Login + onboarding flow bisa diselesaikan end-to-end di production
- [ ] Background job terjadwal (cek di Vercel Cron logs)
- [ ] Tidak ada spike error di Sentry dalam 15 menit pertama setelah deploy
