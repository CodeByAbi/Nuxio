# 11. Frontend Specification

**Asumsi kerja:** dokumen ini mengikuti keputusan final di blueprint MVP — stack Next.js (App Router) monolith, PostgreSQL di Supabase (Supabase Client + RLS, tanpa ORM), Gemini 2.5 Flash untuk AI Copilot, dual segmen Personal/Business, Calendar sebagai landing page (bukan Dashboard). Styling menggunakan Tailwind CSS + shadcn/ui, dipilih karena cocok untuk tim 3 orang dengan timeline 32 hari — shadcn/ui bukan dependency terinstal, melainkan komponen yang di-copy ke repo sehingga bisa dikustomisasi penuh tanpa terkunci ke versi library pihak ketiga.

Bagian implementasi (state komponen, motion, responsive checklist) mengikuti disiplin anti-AI-slop yang diringkas di **11.8** — diekstrak dari dua skill eksternal yang sudah terpasang di skill library lokal (`design-taste-frontend`/taste-skill dan `hallmark`), bukan tools baru yang perlu diinstal ke proyek ini.

## 11.2 Halaman & Komponen (mengikuti Section 4 dan 6 Blueprint)

### Financial Planning Calendar (landing page)

Komponen kunci: `CalendarGrid` (month view), `DayCell` (indikator income/expense/bill/goal sebagai dot, bukan teks penuh — lihat 11.4 Strategi Cluttered Day), `DayDetailPanel` (slide-over panel saat tanggal diklik, berisi list entri + tombol tambah cepat), `ForecastOverlay` (toggle garis proyeksi saldo di atas grid, bukan grafik terpisah).

Ringkasan saldo semua Wallet + status Budget bulan berjalan tampil sebagai strip ringan di atas grid — ini realisasi dari mitigasi risiko "Calendar-only UX belum tentu menjawab kebutuhan snapshot kondisi sekarang" di Section 8 Blueprint, bukan Dashboard baru.

### Wallet

`WalletCard` menampilkan nama, tipe (personal/bisnis untuk Business Workspace), saldo (dari kolom cache, bukan hitung ulang di client). `WalletForm` untuk tambah/edit, dengan opsi arsipkan (bukan hapus permanen — sesuai Business Rule Section 4.3).

### Transaction

`TransactionForm` dipakai di dua entry point (halaman Transaction dan `DayDetailPanel` di Calendar) — **wajib komponen yang sama di-reuse**, bukan dua implementasi form terpisah, untuk menjaga satu sumber kebenaran data sesuai Acceptance Criteria Section 4.4.

### Budget

`BudgetProgressBar` dipakai di dua tempat: halaman Budget penuh, dan sebagai indikator ringkas di `DayDetailPanel`. Warna progress: aman di bawah 80%, warning 80-99%, over 100% — konsisten dengan skema warna semantik aplikasi (lihat 12. UI Design System).

### Goal

`GoalCard` menampilkan progress persentase dan status (`on-track` / `terlambat` jika tanggal target lewat tapi belum 100%). Milestone Goal tampil sebagai `EventBadge` khusus di `DayCell` pada tanggal target.

### AI Copilot

`ChatEntryButton` adalah floating button persisten di seluruh halaman `(app)`, bukan item sidebar biasa — sesuai Section 6 blueprint yang eksplisit meminta entry point kontekstual. `ChatWindow` membawa context halaman aktif (misal tanggal yang sedang dilihat di Calendar) sebagai bagian dari request ke API, supaya pertanyaan seperti "kenapa tanggal ini merah?" bisa dijawab tanpa user mengetik ulang konteks.

### Workspace Settings & Members

Halaman sederhana, non-realtime. `Members` hanya tampil untuk Business Workspace (Personal Workspace tidak menampilkan opsi ini sama sekali, bukan disembunyikan lewat disabled state).

## 11.3 State Management

Karena scope MVP tidak butuh state global kompleks (tidak ada realtime collaboration, sesuai Out of Scope Section 2), pendekatan yang disarankan:

- **Server state**: React Query (TanStack Query) untuk semua data dari API routes — caching, invalidation otomatis setelah mutasi (misal setelah tambah Transaction, invalidate query Wallet balance dan Calendar events sekaligus).
- **Client state lokal**: `useState`/`useReducer` bawaan React untuk UI state murni (modal terbuka/tertutup, tanggal terpilih di Calendar).
- **Tidak perlu** Redux/Zustand global store — kompleksitas tambahan ini tidak sepadan untuk scope MVP dan tim 3 orang.

**Aturan invalidasi kritis**: setiap mutasi Transaction, Budget, atau Goal wajib meng-invalidate query Calendar events dan Forecast — supaya tidak ada tampilan stale antar halaman (mengikuti risiko teknis Section 8: "saldo Wallet ter-cache jadi stale").

## 11.4 Strategi Cluttered Day (Calendar dengan >15 entri)

Sesuai Edge Case Section 4.2, `DayCell` tidak boleh me-render semua badge satu per satu. Strategi:

1. Render maksimal 3 dot/badge kategori (income, expense, bill — masing-masing satu indikator agregat, bukan per-transaksi)
2. Kalau lebih dari batas visual, tampilkan teks kecil "+N lainnya" alih-alih badge tambahan
3. Detail penuh tetap muncul di `DayDetailPanel` saat tanggal diklik — `DayCell` hanya perlu memberi sinyal "ada aktivitas", bukan daftar lengkap

Ini diuji secara eksplisit dengan data dummy padat (>15 entri/hari) sebagai bagian dari Definition of Done UI/UX, bukan diasumsikan aman.

## 11.5 Empty States & Loading States

Sesuai Definition of Done Frontend (Section 9 Blueprint): setiap state kosong wajib punya desain, bukan halaman blank.

| Halaman                                                      | Empty state                                                                                                                                                                                               |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Calendar (user baru selesai onboarding, belum ada transaksi) | Kalender tetap tampil penuh (grid bulan), dengan garis proyeksi Forecast hanya dari income + recurring bill terjadwal, plus catatan kecil "Forecast akan makin akurat setelah beberapa minggu pencatatan" |
| Wallet (belum ada wallet lain selain default)                | Card ajakan "Tambah wallet lain" dengan ikon, bukan list kosong polos                                                                                                                                     |
| Budget (belum ada budget dibuat)                             | Ajakan "Buat rencana pengeluaran pertama" dengan CTA verb-first                                                                                                                                           |
| Goal                                                         | Sama pola — ajakan, bukan "tidak ada data"                                                                                                                                                                |
| AI Copilot (user baru, cold start)                           | Chat tetap terbuka, tapi AI secara eksplisit menyatakan keterbatasan data di pesan pertama (bukan UI kosong menunggu user bertanya tanpa konteks)                                                         |

Loading state: skeleton loader untuk Calendar grid dan list (bukan spinner polos di tengah layar) — supaya perceived performance lebih baik saat data sedang di-fetch.

## 11.6 Responsive Scope

Sesuai Definition of Done: web only, tapi wajib responsive di desktop dan tablet minimum (bukan cuma desktop fixed-width). Breakpoint disarankan:

- Desktop (≥1024px): sidebar penuh + Calendar grid lebar penuh
- Tablet (768px–1023px): sidebar collapsible (ikon saja), Calendar grid tetap grid bulan penuh tapi cell lebih ringkas
- Di bawah 768px: di luar scope MVP eksplisit (Section 2 — tidak ada native mobile), tapi layout tidak boleh rusak total — cukup best-effort, bukan dioptimalkan penuh

**Checklist non-negotiable** (referensi `hallmark/references/responsive.md`, berlaku juga di layout tablet best-effort di atas):

- Tidak ada horizontal scroll di breakpoint manapun — `overflow-x: clip` di `html` dan `body`, **bukan** `overflow-x: hidden` (supaya sidebar `position: sticky` dan popover Calendar tetap jalan).
- Teks yang bisa diklik (item sidebar, tombol CTA, tab filter Transaction) tidak boleh wrap ke 2 baris — kalau label kepanjangan, perpendek dulu sebelum melebarkan elemen.
- Grid/track yang berisi avatar atau ikon (misal grid `WalletCard`) pakai `minmax(0, 1fr)`, bukan `1fr` polos, supaya tidak mendorong layout melebihi viewport tablet.
- Breakpoint ditentukan dari titik Calendar grid mulai pecah secara visual, bukan sekadar breakpoint Tailwind default (`md`/`lg`).
- Elemen full-height (`DayDetailPanel` sebagai `Sheet` di layar sempit) pakai `dvh`, bukan `vh`, supaya tidak lompat saat browser chrome mobile muncul/hilang.

## 11.7 Dependency Antar Komponen (ringkasan untuk sequencing kerja Engineer B)

`CalendarGrid` bergantung pada data dari Wallet, Transaction, Budget, Goal — artinya secara komponen, `CalendarGrid` versi penuh **tidak bisa selesai lebih dulu** dari CRUD dasar keempat entitas itu, meski rendering skeleton-nya (Hari 12 Roadmap) boleh dimulai dari data statis/dummy lebih awal untuk paralelisasi kerja tim.

`ChatWindow` bergantung pada context builder di backend yang mengagregasi ketiga entitas tadi plus Forecast — sehingga secara realistis `ChatWindow` UI boleh dibangun paralel (Week 4 awal), tapi tidak bisa terhubung ke data riil sebelum Forecast engine (Hari 21) selesai.

### Disiplin 8-state komponen interaktif

Berlaku untuk semua elemen interaktif: `DayCell`, tombol, input form (`TransactionForm`, `WalletForm`, `BudgetForm`), `ChatEntryButton`, dsb. Kebanyakan UI AI-generated cuma menstyle default+hover dan lupa sisanya — itu titik di mana interface terasa belum jadi.

| State          | Kapan                  | Aturan                                                                                                                                                                                                   |
| -------------- | ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Default        | diam                   | styling dasar                                                                                                                                                                                            |
| Hover          | pointer di atas elemen | selalu di dalam `@media (hover: hover)` — jangan simulasikan hover untuk device touch; shift kecil warna/border, bukan geometri                                                                          |
| Focus          | keyboard/programmatic  | `:focus-visible` ring 2px, kontras ≥3:1 terhadap elemen dan halaman; **tidak pernah** `outline: none` tanpa pengganti                                                                                    |
| Active/Pressed | ditekan                | `translate`/`scale` kecil (mis. `-translate-y-[1px]` atau `scale-[0.98]`), bukan `box-shadow` glow                                                                                                       |
| Disabled       | tidak interaktif       | opacity 0.5 + `cursor: not-allowed` + `aria-disabled` — selalu ada alasan yang terlihat kenapa disabled (misal tombol submit budget disabled karena field belum valid), jangan disabled tanpa penjelasan |
| Loading        | proses                 | ganti label tombol jadi indikator (bukan tambah spinner di samping label); field input tetap editable saat validasi async berjalan                                                                       |
| Error          | gagal                  | border + ikon + teks — tidak pernah warna saja (align dengan 12.7 Aksesibilitas)                                                                                                                         |
| Success        | selesai                | quiet, tidak perlu perayaan besar — sejalan dengan 12.6 (hindari kata "berhasil", toast singkat saja)                                                                                                    |

**Aturan khusus input field** (form Wallet/Transaction/Budget/Goal):

- Lebar border **konstan** di semua state — jangan ubah `border-width` saat focus, itu memicu layout shift. Sinyal focus datang dari `outline`, bukan border yang menebal.
- Validasi saat `blur`, bukan tiap keystroke. Setelah field "touched" (sudah pernah di-blur), baru revalidate tiap `change`.
- Error message wajib 3 bagian dalam urutan ini: apa yang salah → kenapa (kalau diketahui) → apa yang harus dilakukan user. Satu kalimat kalau memungkinkan.
- Target sentuh minimum 44×44px untuk semua elemen interaktif, termasuk `DayCell` yang bisa diklik di Calendar grid.
- Reserve ruang untuk helper/error text (`min-height` setinggi 1 baris) supaya layout tidak "melompat" saat error muncul/hilang.

### Motion

- Animate hanya `transform` dan `opacity` — jangan animasikan `width`/`height`/`top`/`left` (memicu layout reflow, terasa berat khususnya di Calendar grid dengan banyak `DayCell`).
- `prefers-reduced-motion: reduce` wajib dihormati di semua transisi (skeleton shimmer, reveal `ForecastOverlay`, slide `DayDetailPanel`) — collapse ke opacity crossfade ≤150ms.
- Jangan pakai `window.addEventListener("scroll", ...)` atau simpan posisi scroll ke React state. Kalau nanti ada kebutuhan scroll-driven UI (misal sticky month-header di Calendar), pakai `IntersectionObserver` atau CSS scroll-driven animation.
- Skala durasi: micro 100–150ms (tekan tombol), minor 200–300ms (slide `DayDetailPanel`, buka dropdown), major 300–500ms (buka `Dialog`/`Sheet`). Durasi exit ≈75% durasi enter. Easing: ease-out untuk elemen masuk, ease-in untuk elemen keluar — bukan `ease` bawaan browser yang terasa generik.

### Modal & Overlay (`Dialog`, `Sheet`)

- shadcn/ui `Dialog`/`Sheet` sudah pakai Radix primitives yang menangani focus trap + escape-to-close secara default — jangan override behavior ini secara manual tanpa alasan kuat.
- Konten di belakang modal wajib `inert` supaya tab order tidak bocor dari `DayDetailPanel` ke `DayCell` lain di belakangnya.
- Fokus pertama saat modal terbuka jatuh ke elemen interaktif pertama di dalamnya, bukan ke tombol close.

### Undo over confirm

Karena semua entitas inti (Wallet/Category/Transaction/Goal/Recurring Rule) pakai soft delete (`archived`, lihat CLAUDE.md — tidak ada hard `DELETE`), aksi arsip **tidak perlu dialog konfirmasi**: eksekusi langsung + toast berisi tombol "Batalkan" selama 5–10 detik. Dialog konfirmasi dicadangkan untuk aksi yang benar-benar tidak bisa dibatalkan — di scope MVP ini praktis tidak ada, karena tidak ada operasi hard-delete di API.

### Z-index

Skala bernama, jangan angka acak seperti `z-50`/`z-10`:

```
--z-base:     1     /* konten normal, DayCell default */
--z-raised:   10    /* card hover state, dropdown trigger */
--z-dropdown: 100   /* Select, Combobox popover */
--z-sticky:   200   /* header/sidebar sticky */
--z-modal:    400   /* Dialog, Sheet — termasuk DayDetailPanel */
--z-toast:    500   /* toast konfirmasi/undo */
```

### Dependency & icon discipline

- Cek `package.json` sebelum menambah library baru — jangan asumsikan sebuah package sudah terpasang.
- Satu keluarga ikon per proyek. Nuxio sudah memakai Lucide (default pairing shadcn/ui, lihat 12.4) — jangan campur dengan Phosphor/Tabler/HugeIcons di komponen lain meski taste-skill merekomendasikan Phosphor sebagai default umum; keputusan Lucide di Nuxio sudah final dan konsisten dengan shadcn/ui, bukan area yang perlu diubah.
- Sebelum generate aset visual yang tidak diminta eksplisit di task (logo, avatar/foto profil, ilustrasi, angka/statistik contoh) — tanya dulu, atau pakai placeholder yang jelas ditandai (`[LOGO]`, `[DATA CONTOH]`). Jangan diam-diam menganggapnya versi final tanpa konfirmasi.

### Verifikasi & disiplin proses

- **Jangan patch CSS/source lewat script eksternal.** Kalau butuh ubah fitur UI (misal dark mode), edit langsung di source file tempatnya berada — bukan lewat helper `.py`/`.js` yang melakukan string-replace ke file `.css`/`.tsx`. Script patch yang tertinggal di repo adalah tanda implementasi belum selesai.
- **Verifikasi sebelum menyatakan task selesai**: jalankan/build app, cek tidak ada error di console, uji tiap elemen interaktif yang disentuh, cek breakpoint mobile/tablet dan kedua tema (light/dark) — bukan cuma baca kode dan asumsikan benar.
- **Elemen tanpa fungsi nyata dihapus, bukan dikirim sebagai dead control.** Item sidebar/nav yang menunjuk ke route yang belum ada, tombol yang tidak melakukan apa pun — kalau memang belum waktunya dibangun, jangan ditaruh di UI sama sekali (atau beri label eksplisit "Segera hadir" + komentar `// TODO`), jangan biarkan terlihat berfungsi padahal tidak.
- **Kalau ada theme toggle, kedua mode wajib diverifikasi berfungsi penuh** sebelum ship — Phase 0 sudah pasang `ThemeProvider` (`attribute="class"`, `defaultTheme="system"`, lihat `app/layout.tsx`), jadi setiap komponen baru harus dicek tampilannya di light DAN dark, bukan cuma mode yang sedang aktif saat development.
