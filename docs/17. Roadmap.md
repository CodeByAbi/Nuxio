# 17. Roadmap Engineering

**Status**: Single source of truth untuk implementasi, dari scaffold kosong sampai production.
**Tidak menggantikan**: dokumen lain (Roadmap ini tidak override ADR — kalau Roadmap ini mengambil keputusan atas suatu ambiguitas, `03. Architecture Decisions.md` dan `CLAUDE.md` tetap menang kalau nanti ada perubahan pada dokumen tsb).
**Urutan prioritas dipakai di seluruh dokumen ini**: `CLAUDE.md` → `03. Architecture Decisions.md` (ADR) → keputusan resolusi Roadmap ini sendiri (lihat Roadmap Notes) → dokumen lain.

## 1. Pendahuluan

Nuvio (nama repo `CalBudget`) adalah workspace perencanaan finansial berbasis AI, berpusat pada **Financial Planning Calendar** — satu timeline yang menyatukan transaksi aktual, transaksi terjadwal, tagihan berulang, budget, goal, dan forecast deterministik. AI Copilot adalah narator read-only atas angka yang sudah dihitung domain service; AI tidak pernah menghitung atau menulis data finansial.

Repo saat ini masih scaffold awal: `app/`, `components/`, `lib/`, `types/` masih direktori placeholder, migration Supabase awal masih kosong, app masih menampilkan halaman default `create-next-app`. Tujuh belas dokumen desain (`docs/01.` s/d `docs/16.`, plus `05 Architecture.md`) mendefinisikan produk, arsitektur, database, API, frontend, AI, DevOps, security, dan testing secara detail — tapi belum ada satu dokumen yang mengurutkan semua itu jadi urutan kerja yang bisa langsung dibangun. Roadmap ini adalah dokumen tersebut.

Roadmap ini disusun dengan membaca seluruh tujuh belas dokumen sumber secara utuh, menyilangkan satu sama lain dan terhadap `CLAUDE.md`, lalu meresolusi setiap kontradiksi yang ditemukan jadi satu keputusan konkret dan tidak ambigu (lihat [§4 Roadmap Notes](#4-roadmap-notes)). Tidak ada isi dokumen sumber yang diubah — konflik diresolusi di sini untuk keperluan implementasi, bukan di sana.

## 2. Tujuan Roadmap

- Menyediakan satu backlog berurutan dari repo kosong sampai MVP production-ready, mencakup seluruh 140 FR di `04. PRD.md` dan seluruh keputusan mengikat di ADR.
- Mengurutkan pekerjaan berdasarkan **dependency teknis**, bukan prioritas bisnis — satu phase tidak pernah dimulai sebelum semua yang jadi dependency-nya selesai.
- Membuat setiap phase **lengkap secara vertikal**: database, backend service, API, frontend, shared types, testing, dan dokumentasi untuk domain itu selesai bersamaan. Tidak ada phase "backend-saja" atau "frontend-saja".
- Menghilangkan ambiguitas: setiap kontradiksi yang ditemukan di seluruh dokumen sumber diresolusi jadi satu pilihan konkret di sini, supaya tidak ada dua task di dokumen ini yang saling bertentangan.
- Bisa langsung dipakai sebagai backlog implementasi — setiap task di setiap phase cukup kecil untuk langsung dikerjakan tanpa perlu menerjemahkan ulang scope-nya.

## 3. Cara Menggunakan Roadmap

- **Kerjakan phase secara berurutan.** Phase *N+1* mengasumsikan seluruh Validation Checklist Phase *N* sudah benar. Jangan mulai Phase 5 (Transaction) sebelum Phase 4 (Wallet) lolos checklist-nya — RPC atomic Transaction menulis langsung ke `wallets.cached_balance`.
- **Satu phase belum selesai sampai seluruh Validation Checklist-nya hijau** — migration ter-apply, API hidup, UI berfungsi, test lolos, dokumentasi ter-update. Phase yang setengah jalan (misal DB selesai tapi UI belum) memblokir dimulainya phase berikutnya.
- **Task Backend/Frontend/Database/API/Testing dalam satu phase dimaksudkan dikerjakan bersamaan**, idealnya oleh pemilik vertical slice tersebut, bukan diserahkan berlapis-layer ke orang berbeda secara berurutan.
- **Roadmap Notes (§4) bersifat mengikat untuk project ini.** Kalau ada dokumen sumber yang bertentangan dengan isi task suatu phase, task di phase itu yang benar — konflik dokumen dan resolusinya dicatat di §4 untuk keterlacakan, bukan berarti teks asli dokumen itu yang harus diikuti.
- **Phase 0 dan Phase 15 bukan business domain** — keduanya adalah fondasi tempat semua dibangun, dan hardening pass penutup project. Semua phase lain (1–14) adalah vertical slice dari tepat satu (atau, di kasus yang memang dijelaskan alasannya, dua domain yang sangat coupled) business domain dari `01. Module Specifications.md`.
- **Kontradiksi baru yang ditemukan saat implementasi** harus ditambahkan ke §4 dengan format yang sama (kutipan dokumen → konflik → resolusi), bukan diresolusi diam-diam di kode.

## Phase 0 — Foundation & Project Scaffold

### Goal
Membangun seluruh infrastruktur bersama supaya Phase 1 dan seterusnya bisa membangun vertical slice tanpa perlu menerjemahkan ulang tooling, environment, atau konvensi cross-cutting.

### Overview
Semua phase berikutnya mengasumsikan: CI pipeline yang jalan, tiga environment Supabase sungguhan, TypeScript strict mode, konvensi money/branded-type, error taxonomy, logger, dan helper function RLS — semua sudah ada. Membangun ini sekali di awal menghindari setiap phase domain menciptakan ulang versi yang sedikit berbeda-beda.

### Scope
**Termasuk**: init repo/tooling, CI, 3 project Supabase, konvensi migration dasar, konvensi error/logging/validation bersama, health check, scaffold cron, security headers.
**Tidak termasuk**: tabel atau endpoint business domain apapun (itu mulai dari Phase 1+). Belum ada RLS policy selain helper function `auth_workspace_ids()` itu sendiri (policy dikirim per-tabel, di phase yang membuat tabel itu).

### Dependencies
- Bergantung pada: tidak ada (phase pertama).
- Fondasi untuk: semua phase berikutnya.

### Modules
Tidak ada (infrastruktur cross-cutting, bukan business module doc01).

### Backend Tasks
1. Inisialisasi project Next.js 16 App Router (kalau belum ada di luar scaffold), TypeScript strict mode (`tsconfig.json` `"strict": true`), path alias `@/*`.
2. Install dan konfigurasi ESLint flat config (`eslint.config.mjs`) dan Prettier; hubungkan `npm run lint`.
3. Buat `lib/server/shared/` berisi:
   - `logger.ts` — instance Pino, output JSON, path redaksi untuk `note`, `email`, `display_name`, field apapun yang mengandung `password`/`token`/`key` (RN-11).
   - `errors.ts` — 10 kelas error taxonomy dari `04. PRD.md` §14 (`ValidationError` 400, `AuthenticationError` 401, `AuthorizationError` 403, `NotFoundError` 404, `ConflictError` 409, `DomainRuleError` 422, `RateLimitError` 429, `ExternalProviderError` 502/504, `InfrastructureError` 500, `UnexpectedError` 500), masing-masing sebagai class typed membawa `code`, `message`, `httpStatus`, `field` opsional.
   - `money.ts` — tipe branded `MinorUnitAmount` (`type MinorUnitAmount = number & { readonly __brand: 'MinorUnitAmount' }`) dengan constructor yang memvalidasi integer, `Number.isSafeInteger`, dan non-negatif-atau-positif sesuai konteks pemanggilan (RN-16).
   - `supabase-server-client.ts` — factory Supabase client terikat session-cookie (`@supabase/ssr` `createServerClient`), dipakai setiap service di jalur user-request.
   - `supabase-admin-client.ts` — factory client service-role, hanya dipakai background job; ada guard/komentar level-module yang mendokumentasikan bahwa ini tidak boleh diimpor dari route handler.
4. Buat `lib/server/shared/rate-limit.ts` — limiter sliding-window in-memory (keterbatasan MVP yang diterima sesuai ADR §16, jalur upgrade ke Vercel KV), dengan key generik (identifier, bucket, limit, windowMs).
5. Buat `middleware.ts` — refresh session lewat `createServerClient`, diterapkan ke semua route `(app)`.
6. Buat `app/api/health/route.ts` — `GET`, menjalankan `SELECT 1` lewat admin client, mengembalikan `{ status: 'ok' | 'degraded', db: boolean, timestamp }`.

## Phase 3 — Workspace & Category (Fondasi Tenancy)

### Goal
Setiap user punya minimal satu Workspace (batas multi-tenancy utama), membership dan isolasi workspace ditegakkan di layer app maupun DB, dan setiap Workspace punya set kategori Transaksi yang siap pakai.

### Overview
Workspace adalah "gerbang keamanan paling kritikal" di seluruh sistem (doc01 §3) — setiap tabel finansial mulai dari sini membawa `workspace_id` dan dilindungi model isolasi dua-layer (`workspace-guard` level-app + RLS level-DB). Category digabung ke phase ini khusus karena trigger `handle_new_user` yang membuat Personal workspace user baru juga men-seed kategori default mereka dalam satu operasi atomic — membangun Category sebagai phase terpisah belakangan berarti trigger ini entah belum ada (onboarding rusak) atau harus ditulis ulang dua kali. Sisanya soal Category (CRUD kategori kustom, arsip) cukup kecil untuk masuk nyaman ke daftar task Workspace ini.

### Scope
**Termasuk**: tabel `workspaces`, `workspace_members`, `categories` + RLS; `workspace-guard`; trigger auto-create Personal workspace; RPC pembuatan Business workspace; halaman Settings/Members; CRUD category.
**Tidak termasuk**: tabel apapun yang merujuk `workspace_id` sebagai domain *anak* (Wallet, Transaction, dst — itu phase masing-masing dan mengasumsikan phase ini sudah selesai).

### Dependencies
- Bergantung pada: Phase 1 (Auth), Phase 2 (`user_profiles` harus ada supaya trigger bisa insert ke situ).
- Fondasi untuk: semua phase yang tersisa — semuanya memfilter berdasarkan `workspace_id`.

## Phase 5 — Transaction

### Goal
User bisa mencatat Transaction income/expense yang secara atomic meng-update `cached_balance` Wallet pemiliknya, dengan isolasi workspace dan validasi penuh.

### Overview
Ini ledger inti dan phase paling krusial untuk kebenaran finansial. Setiap domain berikutnya (Transfer, Recurring, Budget, Goal, Forecast, Calendar) menulis ke atau membaca dari `transactions`. Pola RPC atomic yang dibangun di sini (satu Postgres function melakukan insert + update saldo dalam satu transaksi DB) dipakai ulang, tidak diciptakan ulang, oleh setiap phase tulis-berat berikutnya.

### Scope
**Termasuk**: tabel `transactions`, create/update/delete atomic via RPC, `TransactionForm` (dibangun sekali, dipakai ulang nanti di `DayDetailPanel` Calendar), test isolasi workspace.
**Tidak termasuk**: Transfer (tabel/RPC terpisah, Phase 6), occurrence hasil Recurring (Phase 7 — phase ini hanya menangani Transaction yang diinput user).

### Dependencies
- Bergantung pada: Phase 4 (Wallet), Phase 3 (Category, untuk `category_id`).
- Fondasi untuk: Phase 6 (Transfer memakai ulang pola RPC atomic), Phase 7 (Recurring meng-insert Transaction `planned`), Phase 8 (realisasi Budget membaca Transaction), Phase 9 (kontribusi Goal adalah Transaction), Phase 10 (Forecast membaca history Transaction), Phase 11 (Calendar membaca Transaction).

### Modules
Transaction (doc01 §3).

### Backend Tasks
1. `lib/server/transaction/transaction.service.ts`: `listTransactions` (filter tanggal `from`/`to` wajib — tidak pernah query tak-terbatas), `getTransaction` (double-filter berdasarkan `id` DAN `workspace_id`, pola anti-IDOR eksplisit walau sudah ada RLS), `createTransaction`, `updateTransaction`, `deleteTransaction` — ketiga method tulis semuanya memanggil RPC di bawah, tidak pernah menulis langsung.
2. Tegakkan: `amount > 0` selalu, arah lewat `type` (RN-05); `status: 'completed'` dilarang untuk `financial_date` di masa depan (timezone workspace); hanya status `completed` yang mempengaruhi `cached_balance` dan realisasi Budget; mengarsipkan/menghapus Category tidak pernah cascade ke Transaction historis (`category_id` tetap sebagai referensi historis yang menggantung-tapi-valid — `ON DELETE RESTRICT` Category plus soft-delete-saja membuat ini aman by construction).
3. Tidak ada dukungan optimistic UI di sisi server — setiap penulisan adalah round trip request/response normal (sesuai aturan eksplisit doc01 "optimistic UI dilarang untuk mutasi finansial"); ini membentuk API supaya tidak butuh endpoint rekonsiliasi khusus.

### Frontend Tasks
1. `components/transaction/TransactionForm.tsx` — **satu komponen**, nanti dipakai ulang persis di dalam `DayDetailPanel` (Phase 11) — tidak diimplementasikan ulang di sana.

### Database Tasks
1. Migration `0008_transaction.sql`: enum `transaction_type` (`income`,`expense`), enum `transaction_status` (`planned`,`completed`); `transactions(id, wallet_id FK→wallets ON DELETE RESTRICT, category_id FK→categories ON DELETE RESTRICT NULL, goal_id FK→goals ON DELETE RESTRICT NULL, recurring_rule_id FK→recurring_rules ON DELETE RESTRICT NULL, type transaction_type NOT NULL, status transaction_status NOT NULL DEFAULT 'planned', amount bigint NOT NULL CHECK (amount > 0), financial_date date NOT NULL, note text, archived bool default false, created_at, updated_at)`. Catatan: FK `goal_id`/`recurring_rule_id` merujuk tabel yang belum ada sampai Phase 9/7 — migration ini menambahkan kedua kolom sebagai nullable sekarang tapi constraint FK-nya ditambahkan di migration yang membuat `goals`/`recurring_rules` (pengecualian urutan yang memang didokumentasikan, karena `transactions` harus sudah ada sebelum kerja Phase 6 Transfer dan tidak bisa menunggu tabel Phase 7/9).
2. `UNIQUE (recurring_rule_id, financial_date) WHERE recurring_rule_id IS NOT NULL` — kunci idempotency yang dipakai mulai Phase 7 (RN-09: `financial_date`, bukan `due_date`).
3. Index: `(wallet_id, financial_date)` (query rentang), `(financial_date)` (tampilan bulanan), `(category_id, financial_date) WHERE status = 'completed' AND NOT archived` (realisasi Budget, Phase 8), `(goal_id) WHERE goal_id IS NOT NULL` (progress Goal, Phase 9).
4. RLS: tidak ada kolom `workspace_id` langsung di `transactions` — policy lewat subquery melalui `wallets.workspace_id IN (SELECT auth_workspace_ids())`; policy INSERT secara eksplisit melarang `recurring_rule_id` yang di-set client (baris occurrence hanya lewat service-role, dipasang di Phase 7); SELECT/INSERT/UPDATE saja, tidak ada DELETE (soft delete lewat `archived`).
5. RPC `create_transaction(wallet_id, category_id, amount, type, financial_date, note, status)`: `BEGIN` → validasi wallet tidak diarsip (kalau tidak, `WALLET_ARCHIVED`) → validasi `status='completed'` hanya kalau `financial_date <= current_date` di timezone workspace → `INSERT transactions` → kalau `status='completed'`, panggil `applyLedgerMovement` untuk menyesuaikan `wallets.cached_balance` → `COMMIT`.
6. RPC `update_transaction(id, ...)`: atomicity sama — menghitung ulang delta saldo (membalikkan efek lama kalau tadinya `completed`, menerapkan efek baru kalau sekarang `completed`) dalam transaksi yang sama.

## Phase 10 — Forecast & Cron Job 2

### Goal
Setiap Workspace punya proyeksi cashflow yang deterministik, bisa dijelaskan, dihitung ulang berkala, disimpan sebagai snapshot immutable yang dibaca Calendar dan AI Copilot tanpa pernah dihitung ulang sendiri.

### Overview
Forecast secara eksplisit berbasis rule, bukan ML — input yang sama harus selalu menghasilkan output yang sama, bisa diuji unit dengan pasangan input→output tetap. Tidak pernah dihitung secara sinkron saat Transaction ditulis (itu akan merusak target <400ms API); penulisan hanya menandai forecast workspace jadi stale, dan hitung ulang sesungguhnya terjadi di cron job phase ini, yang jalan 10 menit setelah Job 1 (Phase 7) supaya occurrence recurring yang baru ter-generate tersedia sebagai input.

### Scope
**Termasuk**: tabel `forecast_snapshots`/`forecast_entries`, formula deterministik, cron hitung-ulang, penanganan cold-start, API read-only.
**Tidak termasuk**: endpoint apapun yang memicu hitung ulang sinkron — tidak ada, secara sengaja.

### Dependencies
- Bergantung pada: Phase 5 (history Transaction), Phase 7 (occurrence Recurring sebagai input tagihan terjadwal, dan urutan Job 1 → Job 2).
- Fondasi untuk: Phase 11 (`ForecastOverlay` Calendar), Phase 13 (function Cashflow Prediction AI membaca snapshot ini, tidak pernah menghitung sendiri).

### Modules
Forecast (doc01 §3).

### Backend Tasks
1. `lib/server/forecast/forecast.service.ts`: `getLatestSnapshot(workspaceId, walletId?)` — **satu-satunya** jalur baca; tidak ada fallback hitung-saat-baca.
2. `lib/server/forecast/forecast-engine.ts`: pure function `computeForecast(input)` mengimplementasikan formula deterministik: `projectedBalance(date) = currentBalance + Σ scheduledIncome(≤date) − Σ scheduledBills(≤date) − avgDailyNonRecurringExpense × daysFromNow(date)`, di mana `avgDailyNonRecurringExpense` diturunkan dari 30 hari terakhir Transaction expense manual (non-recurring) yang `completed`, `0` kalau tidak ada history (cold start — bukan error). Horizon dibatasi 60 hari walau rentang lebih panjang diminta.
3. `lib/server/jobs/recompute-forecast.job.ts`: memverifikasi `CRON_SECRET`, client service-role, melooping semua workspace, menghitung dan meng-insert snapshot immutable baru + entry per wallet, mengisolasi kegagalan per-workspace, menulis `job_execution_history`. Saat gagal untuk satu workspace, snapshot valid sebelumnya tetap ada — UI tidak pernah menampilkan state kosong, hanya indikator umur kalau stale.

### Frontend Tasks
Tidak ada halaman Forecast khusus (RN-13) — Forecast hanya muncul di dalam `ForecastOverlay` Calendar, dibangun di Phase 11. Task frontend phase ini terbatas pada hook TanStack Query `useForecast` (`lib/hooks/use-forecast.ts`) yang siap dikonsumsi Phase 11.

### Database Tasks
1. Migration `0015_forecast.sql`: `forecast_snapshots(id, workspace_id FK→workspaces ON DELETE RESTRICT, generated_at timestamptz default now(), horizon_days smallint CHECK (horizon_days IN (30,60)))`; `forecast_entries(id, forecast_snapshot_id FK→forecast_snapshots ON DELETE CASCADE, wallet_id FK→wallets ON DELETE RESTRICT, date date, fact_balance bigint, assumed_income bigint default 0, assumed_expense bigint default 0, estimated_expense bigint default 0, projected_balance bigint)`, `UNIQUE(forecast_snapshot_id, wallet_id, date)`. RLS: SELECT untuk member lewat subquery snapshot; **tidak ada policy INSERT/UPDATE/DELETE untuk user biasa sama sekali** — tulis service-role saja, benar-benar immutable dari sudut pandang app.

### API Tasks
- `GET /api/forecast?workspace_id=&wallet_id=` → 200 `{ data: { generated_at, horizon_days, entries: ForecastEntry[] }, meta: { is_cold_start: boolean } }` — `is_cold_start: true` kalau history di bawah 30 hari. **Tidak ada method POST/trigger yang diterima di manapun** — satu-satunya jalur hitung ulang adalah cron job.

### Shared Tasks

## Phase 13 — AI Copilot

### Goal

### Overview
Ini domain leaf project — menghapus `lib/server/ai-copilot/` tidak boleh merusak build apapun yang lain. Dibangun paling akhir di antara phase domain khusus karena kegunaannya bergantung pada Wallet/Budget/Goal/Forecast/Calendar yang sudah benar (sebaliknya tidak berlaku — tidak ada yang lain bergantung ke AI).

### Scope
**Termasuk**: abstraksi `AIProvider`/`GeminiProvider`, Context Builder, structured output + validasi grounding, `/api/ai/chat`, UI chat.
**Tidak termasuk**: history chat tersimpan apapun (client-side saja untuk MVP, trade-off eksplisit — history hilang saat refresh), aksi tulis apapun jenis apapun.

### Dependencies
- Bergantung pada: Phase 4 (Wallet), Phase 8 (Budget), Phase 9 (Goal), Phase 10 (Forecast), Phase 11 (Calendar) — 5 service utama sesuai RN-15.
- Fondasi untuk: tidak ada (leaf sesungguhnya).

### Modules
AI Copilot (doc01 §3).

### Backend Tasks
1. `lib/server/ai-copilot/ai-provider.ts` — interface `AIProvider`: `generateStructuredResponse(prompt, context): Promise<{ narrative, sourceReferences }>` (RN-06).
2. `lib/server/ai-copilot/gemini-provider.ts` — satu-satunya implementasi, `gemini-2.5-flash`, temperature 0.3, max 1024 token, satu kali retry dengan timeout lebih pendek saat gagal sebelum fallback.
3. `lib/server/ai-copilot/context-builder.ts` — `buildFinancialContext(workspaceId)`, menjalankan panggilan paralel (`Promise.all`) hanya terhadap service Wallet/Budget/Goal/Forecast/Calendar (RN-15): `wallets[]` (id, name, currentBalance, type), `summary` (totalBalance, totalIncomeThisMonth, totalExpenseThisMonth, net, forecastedLowestBalance/Date), `topCategories[]` (top 5, lewat method agregat Wallet/Transaction, bukan panggilan langsung AI→Transaction), `budgets[]` (status: on_track/warning/exceeded), `goals[]` (progress, isOnTrack), `upcomingBills[]` (14 hari ke depan, lewat method agregat Calendar/Recurring), `dataQuality` (`hasEnoughHistory`: ≥14 hari, `oldestTransactionDate`, `totalTransactionCount`). Tidak pernah mengirim baris `transactions` mentah.
4. `lib/server/ai-copilot/ai-copilot.service.ts` — mengorkestrasi: bangun context → susun system prompt (angka hanya dari blok data yang disuntikkan, maksimal 4 kalimat kecuali detail diminta, format Rupiah, CTA singkat) → panggil `AIProvider` → validasi.
5. Tiga function, dipicu keyword matching level-server (bukan deteksi intent sisi LLM): **Spending Analysis** (memakai `topCategories`/`budgets`/`summary`), **Cashflow Prediction** (memakai `summary.forecastedLowestBalance/Date` + `upcomingBills` — **wajib** memanggil `getLatestSnapshot` `forecast.service.ts`, tidak pernah menghitung proyeksi sendiri — ini baris paling kritis-keamanan di phase ini), **Budget Recommendation** (memakai rata-rata historis `topCategories` + disclaimer wajib "saran berdasarkan pola historis, bukan aturan pasti").
6. `lib/server/ai-copilot/validate-response.ts` (hybrid RN-07): ekstrak setiap angka dari `narrative`, konfirmasi masing-masing ada di object `FinancialContext` yang dikirim; cek frasa indikator-tulis ("saya sudah buat...", "saya simpan...") → `hasActionableWrite`; cek `narrative.length` <500 kata. Kalau `hasHallucinatedNumbers` atau `hasActionableWrite`: **response tidak pernah dikirim ke client** — pesan fallback dikembalikan sebagai gantinya, dan insiden dicatat (Pino + Sentry) untuk review manual.
7. `sanitizeChatInput` — pembersih prompt-injection berbasis regex (pola untuk "abaikan instruksi," "kamu sekarang," "berpura-puralah jadi," padanan Bahasa Indonesia) + batas input 1000 karakter, diterapkan sebelum pesan mencapai context builder atau model.
8. Rate limit: 20 pesan/user/jam (memakai ulang rate limiter Phase 0).

### Frontend Tasks
1. `components/ai-copilot/ChatEntryButton.tsx` — tombol floating persisten di setiap halaman `(app)`, bukan item sidebar.
2. `components/ai-copilot/ChatWindow.tsx` — membawa context halaman aktif (tanggal saat ini, halaman saat ini) di requestnya; history multi-turn disimpan di React state saja, dibatasi 10 turn, hilang saat refresh (trade-off yang didokumentasikan, bukan bug).
3. `components/ai-copilot/ChatBubble.tsx` — bubble AI/user dibedakan lewat posisi + background netral slate/indigo terang (sengaja bukan warna status); setiap klaim numerik dapat indikator kecil "terhubung ke data" memakai `sourceReferences`.
4. Disclaimer Budget Recommendation dirender sebagai `text-xs text-slate-500` kecil, bukan kotak warning (sesuai doc12 §12.5 — disclaimer AI eksplisit tapi tidak mengkhawatirkan).
5. State cold-start: saat `dataQuality.hasEnoughHistory` false, balasan secara eksplisit dan jujur mengakui keterbatasan data — ditegakkan di logic `ai-copilot.service.ts`, tidak diserahkan model untuk menyimpulkan sendiri.

### Database Tasks
Tidak ada — AI Copilot secara eksplisit stateless di MVP (tidak ada tabel chat-history, tidak ada tabel prompt-log).

### API Tasks

Risiko utama di tahap ini adalah menemukan gap yang terlalu besar untuk ditutup sebelum tanggal launch yang sudah dikomitmenkan — dimitigasi dengan phase ini ada sebagai pass nyata terjadwal, bukan asumsi implisit "kita akan sadar kalau ada yang salah."

### Technical Notes
Phase ini seharusnya sedikit mengejutkan kalau Validation Checklist setiap phase sebelumnya memang benar-benar ditegakkan — tujuannya konfirmasi di level sistem-yang-dirakit, bukan penemuan pertama bug level-domain.

### Estimated Complexity
**Medium** — mayoritas verifikasi dan eksekusi checklist bukan engineering baru, tapi drill backup/restore dan sesi manual QA penuh adalah investasi waktu tidak trivial yang tidak boleh dilewati atau diburu-buru.

## 6. Definition of Done (Level Project)

Project production-ready kalau **semua** berikut berlaku bersamaan (disintesis dari doc02 §16, doc04 §20, dan checklist DoD masing-masing phase di atas):

**Kelengkapan fungsional**
- Semua 16 fitur / 15 module doc01 + Settings + Plan Gating diimplementasikan end-to-end (Phase 1–14 semua lolos Validation Checklist masing-masing).
- Semua 140 FR dari `04. PRD.md` §7 terverifikasi terhadap implementasi yang sudah jadi.

**Kebenaran finansial**
- Uang adalah `bigint` di DB, tipe branded `MinorUnitAmount` di batas API/domain, tidak pernah float/decimal di manapun (RN-16).
- Setiap penulisan finansial multi-entitas (Transaction+saldo, Transfer, kontribusi Goal) atomic lewat RPC Postgres, terverifikasi di bawah test kegagalan-yang-dipaksa.
- Forecast deterministik dan diuji unit untuk output identik byte-per-byte pada input identik.
- Tidak ada tabel `goal_contributions` (RN-08); tidak ada transaction manapun yang arahnya bukan turunan dari `type` (RN-05).

**Keamanan**
- Isolasi workspace dua-layer (`workspace-guard` level-app + RLS level-DB) terverifikasi independen di setiap tabel finansial.
- Akses cross-workspace mengembalikan 404, tidak pernah 403 (RN-02), terkonfirmasi di setiap endpoint ID-bearing.
- Nol temuan kebocoran data cross-workspace — release blocker keras, bukan bug yang bisa ditunda.
- Semua secret ter-scope benar per environment; tidak ada yang bisa dijangkau dari bundle client; secret-scanning bersih.
- Rate limiting aktif di endpoint register/login/AI-chat/mutasi-finansial/GET sesuai limit yang terdokumentasi.

**Keamanan AI**
- `lib/server/ai-copilot/` bisa dihapus tanpa merusak build module manapun yang lain.
- 100% response AI melewati structured output + validasi grounding sebelum mencapai client; toleransi nol untuk angka tak-bersumber.
- Nol jalur tulis dari AI, terverifikasi lewat code review maupun test otomatis no-state-change.

**Gate kualitas**
- CI (typecheck → lint → test → build) hijau di release candidate, <3 menit.
- Coverage unit domain service ≥80%; overall coverage ≥65%.
- Set skenario Manual QA penuh (doc16 §16.6, dikoreksi sesuai RN-02) dieksekusi tanpa blocker.
- Performa terverifikasi terhadap setiap target p95 doc02 §2 pada volume data realistis.
- WCAG 2.1 AA terverifikasi di Calendar, form, dan navigasi.

**Kesiapan operasional**
- Tiga environment Supabase sepenuhnya terpisah (dev/staging/prod), tidak pernah ada environment yang menunjuk ke data production untuk testing.
- Kedua cron job (`generate-recurring`, `recompute-forecast`) jalan sesuai jadwal, termonitor lewat `job_execution_history` + Sentry.
- Backup harian terjadwal; restore terverifikasi minimal sekali di staging.
- `/api/health` hidup dan di-poll uptime monitor.
- Deployment pipeline (CI → auto-deploy staging → manual QA → approval manual → production) dijalankan end-to-end minimal sekali tanpa insiden.

**Dokumentasi**
- Semua Validation Checklist Roadmap ini tercentang.
- Kontradiksi apapun yang ditemukan saat implementasi yang belum ada di §4 sudah ditambahkan di situ, mengikuti format yang sama.
